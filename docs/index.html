Serve an h5i App as an RL Environment

senv runs an h5i-app kernel behind the OpenEnv wire. The kernel decides every reward and every done, so h5i app prove reaches the numbers a policy is trained on.

Rust libraryOpenEnv 58d03440 · h5i-app 0.5.5 · Rust 1.88+
Where it fits. senv is part of h5i app. The kernel contract, extraction, proofs and mutation testing are the ordinary h5i app ones. senv replaces the Axum routes with an OpenEnv server, so the unmodified OpenEnv Python clients can train against the kernel.

An RL environment is a state machine that also hands out rewards. If the reward is computed in the server code that renders observations, nothing checks it but tests. If it is a field the kernel commits, a Lean theorem about the kernel covers it for every input: that a reward stays in range, that only a correct answer pays, that every episode ends.

1. Lay the environment out like any h5i app

An environment is a kernel crate and a server crate. The kernel crate has no web or database dependencies: it holds the snapshot, command, reply and error types and a pure transition, kept in the Aeneas subset so h5i app extract can translate it. The server crate implements h5i_app::Kernel for a marker type and senv::Environment for the shell.

OpenEnv reset/step → senv::Environment → kernel transition(snapshot, command)
                                                ↓
                       committed snapshot (reward, done) → observation

Environment turns a reset or step into a kernel command and renders what the kernel committed. The binary is one call:

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    senv::run(MyEnv::default(), senv::ServeArgs::from_env_and_args()).await
}

Each OpenEnv session runs on its own MemoryEngine, so a property of the kernel holds per episode, and disconnecting drops the engine. senv::Session drives the same kernel and rendering without a socket, for tests and Rust rollouts.

2. Prove the rewards

In examples/wordle, the reward the agent sees is the field the step committed:

// examples/wordle/kernel/src/lib.rs, in transition:
Command::Step { mv } => match step_core(game, mv) {
    Ok((next, phase)) => Ok((
        Some(next),
        Reply {
            reward_milli: next.reward_milli,
            done: next.done,
            phase: Some(phase),
        },
    )),
    Err(e) => Err(e),
},

so a theorem about the extracted transition is a theorem about that reward:

-- examples/wordle/proofs/Theorems.lean
/-- Every reward a step commits is between 0 and 1000. -/
theorem reward_in_range (c : Core) (mv : Move) :
    transition () c (.Step mv) ⦃ r => ∀ c' rep, r = .Ok (some c', rep) →
      0 ≤ rep.reward_milli.val ∧ rep.reward_milli.val ≤ 1000 ⦄
cd examples/wordle
h5i app extract
h5i app prove     # the 13 theorems in h5i-app.toml, plus panic-free and read-only
h5i app mutate    # 10 planted bugs; each must break a proof

Besides the range, the Wordle proofs show that guesses are marked by the TextArena rule, that a guess pays 1000 exactly when it is the secret, that a repeated guess is never scored, and that every game ends. The mutants include a loss that pays like a win and a secret that changes mid-game.

What the proof covers

A theorem covers the extracted kernel. It does not cover the shell: message parsing, the word list, the secret chosen for a seed, or the rendering of observations. Isolation between sessions is a separate engine per session, checked by tests rather than proved. senv implements a subset of the OpenEnv wire: no HTTP /reset, /step or /state, no CORS, no web UI. The differences are in the protocol note.
